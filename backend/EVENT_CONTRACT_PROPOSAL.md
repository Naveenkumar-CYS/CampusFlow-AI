# Student Event Contract — PROPOSED, NOT YET AGREED

This is a draft for discussion with Person B. Nothing here is final until
we both sign off on it. Treat every field name and event name as
negotiable.

## Envelope (shared by all events)

```json
{
  "event_id": "uuid",
  "event_type": "student.created",
  "schema_version": "1.0",
  "timestamp": "2026-08-22T20:12:11Z",
  "student_id": "STU001",
  "data": { }
}
```

| Field | Type | Notes |
|---|---|---|
| event_id | uuid | Unique per event, generated by producer |
| event_type | string | dot-separated, e.g. `student.created` |
| schema_version | string | bump on breaking payload changes |
| timestamp | ISO-8601 | UTC, when the event was produced |
| student_id | string | the human-readable enrollment number, not the internal UUID |
| data | object | event-specific payload, see below |

## Events

### `student.created`
- **Purpose:** a new student record was created.
- **Producer:** Student service (this backend).
- **Example consumers:** Fees module (open a fee account), Hostel module
  (make student eligible for allocation), notification module (welcome
  email — not built yet).
- **`data` payload:** full student record — `id`, `student_id`, `name`,
  `email`, `department`, `course`, `enrollment_year`, `phone`.

### `student.updated`
- **Purpose:** an existing student record changed.
- **Producer:** Student service.
- **Example consumers:** any module caching student info (fees, hostel,
  exams) needs to know a field changed.
- **`data` payload:** `id`, `student_id`, and only the fields that
  changed (open question for Person B: full record vs. diff-only — see
  below).

### `student.deleted`
- **Purpose:** a student record was removed/deactivated.
- **Producer:** Student service.
- **Example consumers:** downstream modules should stop referencing the
  student / archive dependent records.
- **`data` payload:** `id`, `student_id` only.

### `admission.created`
- **Purpose:** a new admission application was submitted.
- **Producer:** Admission service.
- **Example consumers:** review/queueing tooling, notification module
  (not built yet).
- **`data` payload:** full admission record.

### `admission.updated`
- **Purpose:** an admission's fields changed (not a status transition —
  see `admission.approved`/`admission.rejected` for those).
- **Producer:** Admission service.
- **`data` payload:** `id`, `application_number`, and changed fields
  (same full-vs-diff question as `student.updated` below).

### `admission.approved`
- **Purpose:** an admission was approved. In the current Day-2
  implementation this is also the moment a Student record gets
  auto-created/linked — once this becomes a real event, this is the
  natural point downstream services (fees, hostel) would react to
  provision their own records.
- **Producer:** Admission service.
- **`data` payload:** `id`, `application_number`, `student_id` (the newly
  linked/created student).

### `admission.rejected`
- **Purpose:** an admission was rejected. No Student is created.
- **Producer:** Admission service.
- **`data` payload:** `id`, `application_number`.

## Where event publication would go (not implemented yet)

Both `student.py` and `admission.py` service modules are the natural
publication points — e.g. inside `admission_service.update_admission`,
right after the status transitions to `APPROVED`, is where an
`admission.approved` event would be emitted once we have a transport.
No publishing code exists yet; this is purely marking where it belongs
architecturally so it's a small addition later rather than a rewrite.

## Open questions for Person B

1. Transport: Kafka, RabbitMQ, or simple webhook/HTTP callbacks? This
   backend doesn't publish anything yet — CRUD only, Day 1.
2. `student.updated` — full record snapshot each time, or a diff of just
   the changed fields?
3. Is `student_id` (human-readable) the right join key across modules,
   or should everything key off the internal UUID instead?
4. Do we need a `student.deactivated` distinct from `student.deleted`
   (soft delete vs hard delete)? Nothing is implemented for deletes yet
   in this service.
